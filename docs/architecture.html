01 The pipeline

Four input formats collapse into one contract before any reasoning happens, so the extractor never needs to know whether a report arrived as a spreadsheet or a photograph. The dashed hop is the only place the OCR model is ever called.

02 The trust gate

Nothing reaches the schedule unexplained. Five checks run in a fixed order, and the first one that trips decides the verdict — so a flagged conflict can never be overridden by a confident-sounding extraction.

03 Five agents, three without a model

Two agents call an LLM. The other three are deterministic code — which is the point: “evidence-backed validation” has to mean a check you can re-run and argue with, not a model grading its own homework.

Where the vocabulary comes from. The normalizer’s rules, all ten conflict types and the three trust verdicts are read from the domain team’s ontology workbook — 15 L5/L6 activities, 45 terminology variants, 30 benchmark cases, 10 conflict pairs. None of it is invented in code.

Three consecutive runs returned identical results. At temperature 0.1 the same input gave three different answers, which made every delta partly noise — the repeatability is what lets the domain team trust a six-point change.

The one miss is a boundary, not a defect. Case B014, “Cable pulling in Substation B finished.”, expects MATCH and gets REVIEW. The answer key pairs with an expected activity id, so it is a post-match decision; this service emits pre-match trust. Telling “no asset tag but unambiguous” from “no asset tag and two candidate assets” needs the schedule candidate set, which belongs to the matcher. 93% is the honest ceiling here.

Activity-matching accuracy and schedule-impact accuracy are not measured on this page. They belong to the matcher and CPM services.

Four roles behind JWT and bcrypt: a field supervisor submits and reads, a planner also reviews and imports the schedule, a project manager reads, admin does everything. Every capture, extraction and import writes a row that is never updated and never deleted — that is the answer to “where did this progress number come from?”

06 Known gaps

  • untestedVoice. The audio path is written but has never been executed once. Needs one real recording before it can be claimed.
  • bluntPhotographed tables. A four-row DPR photo sends all its events to review, because the “more than one activity” rule was written for prose. Excel rows are unaffected — they already extract one row at a time.
  • heldThe 16 held-out benchmark cases. Deliberately unrun. Tuning against a test split turns it into a training split.
  • opsNot yet a service. The API runs as a foreground process; demo day needs it supervised.
Also open, by design. The extractor still fills foundation_id and equipment_id correctly, but the ontology only ever uses asset_tag — so the benchmark never exercises those fields. They are verified by hand, not by the suite.
